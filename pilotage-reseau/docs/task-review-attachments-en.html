Task-Review Attachments

The consultant marks up the photo a shop sent, frame by frame, each frame carrying a severity and a note. Today that work cannot leave the cockpit. This is what the panel API needs to expose so the shop actually receives it.

1 · Why

A consultant reviews the photo a shop uploaded when completing a checklist task. Reviewing means pointing at things: this shelf, that price tag, that tray. The cockpit lets the consultant drop numbered frames on the photo, give each frame a severity from the existing scale — minor / major / critical — and write one line per frame. Colour and stroke follow the severity, so a shop manager can read the picture before reading the text.

Measured state of the API. POST /consultant/shops/{shopId}/task-reviews accepts only rating, is_accepted, comment, checklist_id and completion_id. No attachment-upload route is exposed anywhere on the consultant surface. So the annotated photo stays in the cockpit database, and the only thing that reaches the shop is a block of text listing the marker numbers — numbers that refer to a picture the shop cannot see.

The one-line ask

Let a consultant attach a file to a task review, and let the shop see it. Everything below is detail around those two sentences.

3 · The marker model

Markers are stored and sent as vector data, not burnt into the pixels. Two reasons, both practical: a flattened photo cannot be re-edited or re-coloured later, and flattening in the browser is blocked by the storage CORS policy anyway (§5). The panel should keep the overlay next to the file and hand it back untouched.

Coordinates are fractions of the image (0 → 1), never pixels: the same overlay renders on a phone, a tablet and a printout without recomputation.

{
  "version": 1,
  "image": { "width": 1600, "height": 1200 },
  "markers": [
    {
      "n": 1,                      // display number, 1-based, stable
      "x": 0.062, "y": 0.104,      // top-left corner, fraction of width / height
      "w": 0.241, "h": 0.238,      // size, fraction of width / height
      "level": 2,                  // severity, same scale as rating (1..5)
      "text": "Top shelf: 40 cm gap, epicerie range not faced up."
    },
    { "n": 2, "x": 0.55, "y": 0.42, "w": 0.19, "h": 0.20, "level": 3,
      "text": "Price tag missing on the confiture line." }
  ],
  "author": { "id": 12, "name": "Sam V." },
  "created_at": "2026-08-17T18:54:52+02:00"
}

Validation the panel should apply: 0 ≤ x, y < 1, 0 < w, h ≤ 1, x + w ≤ 1, y + h ≤ 1, level ∈ {1..5}, text ≤ 400 characters, at most 40 markers. Reject with 422 rather than clamping silently — a clamped frame points at the wrong shelf.

4 · Endpoints requested

Response 201:

{

  "kind": "annotated_photo",
  "mime": "image/jpeg",
  "bytes": 248113,
  "width": 1600,
  "height": 1200,
  "url": "https://…?X-Amz-…",
  "url_expires_at": "2026-08-17T19:54:52+02:00",
  "shop_id": 4,
  "created_at": "2026-08-17T18:54:52+02:00",
  "client_ref": "cockpit-4-1213-20260817-1"
}

The returned id must work as-is with GET /attachments/{id}/presigned-url, which already exists and which the cockpit already uses for completion photos.

Why a separate upload

A consultant annotates before deciding the rating. Uploading first and linking after means the annotation work is not lost when the rating is refused at validation — a comment is mandatory below the compliance threshold, for instance. An attachment still unlinked after 24 h may be purged; the cockpit does not rely on it living longer than that.

4.2 · Upload straight onto an existing review

POST/consultant/shops/{shopId}/task-reviews/{reviewId}/attachments

Same fields, same constraints as §4.1. The response carries review_id and task_id in addition. This is the endpoint asked for by name — on its own it is not sufficient, see §4.3.

4.3 · Attach at review creation

POST /consultant/shops/{shopId}/task-reviews should accept one extra field, attachment_ids:

{
  "task_id": 1213,
  "review_date": "2026-08-17",
  "rating": 2,
  "is_accepted": false,
  "comment": "1. [major] Top shelf: 40 cm gap…",
  "checklist_id": 57,
  "completion_id": 561,
  "attachment_ids": [91234]
}
Why both paths

Without attachment_ids at creation, rating a task with an annotated photo takes two calls, and the second one can fail: the review is gone, the photo is not, and the franchisee reads a comment referring to numbers they cannot see. With both paths available the cockpit follows the order the user actually worked in.

An attachment_id already linked to another review ⇒ 422, code attachment_already_linked.

4.4 · Read the attachments of a review

GET/consultant/shops/{shopId}/task-reviews/{reviewId}/attachments 
{ "attachments": [ {
  "id": 91234, "kind": "annotated_photo", "caption": "…",
  "mime": "image/jpeg", "bytes": 248113, "width": 1600, "height": 1200,
  "url": "https://…", "url_expires_at": "…",
  "overlay": { "…": "see §3" },
  "created_by": { "id": 12, "name": "…" }, "created_at": "…"
} ] }

These attachments must also surface in GET /consultant/shops/{shopId}/checklists/{checklistId}/progress?date=…, the feed the cockpit already reads to know the state of a task. Otherwise finding out whether an annotation exists costs one extra call per task, on a screen that lists a hundred and fifty of them. A single review_attachment_count on each progress row is enough.

4.5 · Delete

DELETE/consultant/shops/{shopId}/task-reviews/{reviewId}/attachments/{attachmentId}

Returns 204. Restricted to the author of the review and to management. An attachment the shop has already seen is not physically deleted but flagged deleted_at — the audit trail of a quality control must not be able to vanish.

5 · Reading from a browser — CORS

Decisive — please do not skip

Photos are served by a signed storage URL (…r2.cloudflarestorage.com/…) which today returns no CORS header. A browser can display the image, but any JavaScript processing is forbidden: drawing the photo into a canvas taints it and the export fails. That is precisely why the cockpit stores its annotations as vectors instead of flattening the image client-side.

Either answer solves it:

  1. Access-Control-Allow-Origin on the storage responses, ideally restricted to the panel and cockpit origins; or
  2. a content route served by the panel itself — GET /attachments/{id}/content — returning the bytes with the right Content-Type and the CORS header.

The second is preferable: it survives a change of storage provider and avoids exposing the bucket configuration.

6 · Shop-side visibility

To be confirmed explicitly, because it is the whole point of this work: a review attachment must be visible to the shop in the field application, next to the review comment. If it is not today, it needs adding — without it the upload endpoint serves no purpose. Ideally the shop is notified when a review carries an attachment.

7 · Acceptance checklist

  • A consultant can upload a file for a shop before any review exists, and gets an id back.
  • That id can be passed as attachment_ids when creating the review, in the same call.
  • A file can also be uploaded onto a review that already exists.
  • The overlay JSON comes back exactly as it was sent.
  • The progress feed says how many attachments a review carries, without an extra call.
  • Deleting flags deleted_at instead of erasing, once the shop has seen the file.
  • The image bytes are readable from a browser on another origin — CORS header or panel-served content route.
  • The shop sees the attachment in the field application, beside the review comment.
